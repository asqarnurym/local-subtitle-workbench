# План доработки local-subtitle-workbench

Версия: 02.11.2026. Основа: аудит репозитория (commit c7656b1), Индивидуальный план магистранта, литература 2026 г. (FA-Bench, FuseAlign, «Where Words Begin and End»), пилоты и полные прогоны 29.10.2026; воспроизводимость и дополнительный анализ 01–02.11.2026.

Метрики оценки — только из Плана: **среднее отклонение границ от эталона (MAE, мс)** на уровне слов и фонем, с 95% CI, и **доля границ в пределах 20 мс (Acc@20ms)** как проверка цели «<20 мс». Сравнение методов — парный тест Уилкоксона с поправкой Холма. Время этапов и RTF записываются для прозрачности по решению автора, не как целевые показатели. VRAM/RAM, MedAE, RMSE, Acc@50/100 не являются метриками оценки статьи. Для головы надёжности BRQE дополнительно: ROC-AUC, PR-AUC и кривая «доля отбракованных слов → MAE оставшихся» (§6).

## 0. Принцип

**Одна статья, один пайплайн.** Статья пишется для журнала. ML-звено (BRQE, §6) — последний шаг Proposed, а не отдельная версия работы. Выключатель `--refiner none|brqe` нужен только для абляции «Proposed без BRQE / с BRQE» в той же таблице того же замороженного прогона.

```
Proposed: VAD → Whisper → якорение (DTW/NW) → чанкинг → MFA → BRQE (уточнение + надёжность) → сшивка → экспорт
Base:     B0 Whisper, B1 Whisper+CTC, A1 текст+CTC
Эталон:   TIMIT-sample (160), Buckeye (20 тестовых дикторов)
Подысследования после заморозки: S1 дрейф, S2 темп, S3 размер ASR, S4 акцент (silver), S6 шумы
```

Никаких фолбеков: сбой шага = ошибка, фиксируется в `benchmark_utterances.json`.

## 6. BRQE — Boundary Refinement & Quality Estimation (часть Proposed)

### 6.1. Обоснование
- Около 30% границ MFA (A2, пилот Buckeye) дальше 20 мс; MFA работает на 10-мс сетке. Уточнение по спектрограмме — классическая идея (нейросетевое уточнение после HMM-выравнивания), в 2026 г. актуальная (FuseAlign, «Where Words Begin»).
- Единственное место пайплайна, где обучаемый слой бьёт прямо в метрику Плана (§5, разбор слоёв).
- Голова надёжности полезна для доступности независимо от выигрыша уточнения: помечает слова для ручной проверки субтитров.

### 6.2. Вход и модель
- **Вход:** окно лог-мел-спектрограммы ±100 мс вокруг каждой границы MFA (слова и фонемы) + контекст: фонемы слева/справа, длительности, тип границы (начало/конец).
- **Модель (основная):** лёгкая 1D-CNN, две головы: (1) регрессия поправки Δt; (2) P(|ошибка MFA| > 20 мс).
- **Вариант энкодера (если CNN даст мало):** замороженные SSL-признаки (wav2vec2 / HuBERT / WavLM base, извлекаются один раз) + малая голова.
- Torch уже в extra `speech`; новые зависимости не нужны.

### 6.3. Данные
- Обучение: 20 обучающих дикторов Buckeye, MFA с эталонным текстом (как A2), цели — ручные границы. Обучать на MFA-silver нельзя.
- Тест: 20 тестовых дикторов Buckeye (в полном прогоне) + TIMIT без дообучения (переносимость).
- Применение: к выравниваниям MFA и в A2, и в B2.

### 6.4. Соперники (обязательны в статье)
1. MFA без поправки (A2, B2).
2. **Константная поправка:** средний сдвиг MFA по типу границы, выученный на обучающих дикторах. BRQE должен её обойти, иначе нейросеть не обоснована.
3. (Опционально) градиентный бустинг на ручных признаках — требует scikit-learn (решение автора, §8).

### 6.5. Правило решения (до заморозки, без тестовых дикторов)
5-кратная кросс-валидация **по дикторам внутри обучающих 20**. Гиперпараметры выбираются там же и фиксируются.
- Если уточнение снижает MAE слов относительно константной поправки **в обоих сценариях (A и B)**, с парным Уилкоксоном по 20 обучающим дикторам (MAE каждого диктора, когда он в отложенном фолде) **p < 0.05** — BRQE (обе головы) входит в Proposed. Реализация: `scripts/train_brqe.py --cv 5`, функция `decide` (зафиксировано 29.10.2026 до получения чисел CV).
- Если нет — в Proposed входит только голова надёжности; уточнение описывается в статье как отрицательная абляция.
Решение и числа CV записываются в этот план до тега.

**Результат CV (29.10.2026, `reports/brqe_cv_20260401.json`).** Данные: прогон `reports/brqe_train_run` (3000 клипов, 20 обучающих дикторов; A2: 0 сбоев, B2: 10 сбоев, покрытие слов 91.2%). 461 850 границ, из них 382 270 сопоставлены с эталоном. Гиперпараметры — значения по умолчанию `TrainConfig` (12 эпох); подбор не проводился. Числа — MAE по границам (мс) / Acc@20ms (%), объединённые по отложенным фолдам:

| | нет | константа | BRQE |
|---|---|---|---|
| слова A | 18.71 / 70.6 | 18.68 / 71.0 | **16.46 / 76.7** |
| слова B | 24.46 / 69.5 | 24.43 / 70.0 | **22.32 / 75.5** |
| фонемы A | 14.95 / 80.2 | 14.96 / 80.5 | **13.77 / 82.3** |
| фонемы B | 20.16 / 79.3 | 20.16 / 79.5 | **19.00 / 81.3** |

BRQE против константы: улучшение у 20/20 дикторов во всех четырёх срезах, Уилкоксон p = 9.6·10⁻⁵ (нормальная аппроксимация исходной реализации CV, не минимальное возможное точное p). Голова надёжности: ROC-AUC 0.780 (слова), 0.769 (фонемы); PR-AUC 0.618 / 0.487 при доле положительных 0.299 / 0.203. Уточнение описания 02.11.2026: сам отчёт CV и решение по нему не меняются; точное двустороннее p при 20 ненулевых разностях одного знака равно 2/2²⁰ ≈ 1.907·10⁻⁶.
**Решение: уточнение входит в Proposed (оба сценария выполнили правило).**
Оговорки: (1) MAE здесь считается по отдельным границам до разрешения перекрытий, поэтому не совпадает с метрикой бенчмарка; итоговые числа даёт прогон на тестовых дикторах. (2) Прогон обучающих данных запущен на коммите `5c24610`; код путей A2/B2 до `9dc8018` не менялся (менялся только модуль BRQE).

**Gap, который проект закрывает (честная формулировка):**
1. Оценки выравнивателей обычно ведутся на коротких фрагментах, часто по клипам и без статистики по дикторам. Выбор, практически главный для субтитров, — известен ли текст или есть только ASR — редко сравнивается в одном пайплайне на ручных границах. У нас: оба сценария, TIMIT и разговорный Buckeye, статистика по дикторам.
2. Выравниватели не сообщают, насколько можно доверять каждой границе. BRQE уточняет границы и даёт оценку надёжности; проверен на отложенных дикторах при замороженных весах и сравнён с постоянным сдвигом.
3. Длинные записи: что ломается при нарезке на чанки и чего стоит стык (S1/S1b). Находка S1 сама по себе — результат.
4. Локальная работа на обычном железе — свойство системы, а не научный вклад. В gap не выносится.

- Около стыков ошибка выросла у всех 19 сравнимых дикторов A2.

**Находка для статьи (RQ3) — фиксируется.**
- Нарезка на чанки ≤ 30 с с запасом 0,5 с без текста стоит около 110–125 мс ошибки около стыков и вдвое повышает ошибку вдали от них.
- Тот же MFA на целой 60-секундной записи одним чанком даёт A2 ≈ 17–19 мс, как на коротких фразах.
- Значит, на минутных записях длина сама по себе не мешает: точность портит нарезка.
- Формулировка для CLAIM_LEDGER — только после одобрения автора.

**Разбор механизма** (микротест на 6 записях, `reports/seam_micro/`, не версионируется):
1. **VAD не видит пауз.** Пайплайн вызывает Silero-VAD из faster-whisper 1.2.1 с параметрами по умолчанию, кроме `min_silence_duration_ms`. По умолчанию `speech_pad_ms = 400`: каждый участок речи расширяется на 0,4 с с обеих сторон. Поэтому пауза короче примерно 1,2 с не попадает в список. На 6 из 6 записей найдено 0 пауз.
2. **Без пауз стык ставится посреди речи.** В сценарии A это граница псевдосегментов по 40 слов: чанки по 80 или 120 слов. В сценарии B это граница сегментов Whisper. Место стыка определяется по временам Whisper с погрешностью в сотни миллисекунд.
3. **Запас 0,5 с у такого стыка содержит речь соседа без текста.** MFA вынужден разместить свой текст поверх чужой речи и сдвигает границы, иногда на несколько секунд от стыка.
4. **Исправленная сшивка устраняет только последствие** (пересечения и падения), но не причину.

С `speech_pad_ms = 30` VAD находит от 1 до 8 пауз на запись, и 10 из 12 стыков выборки попадают в паузу.

**Варианты исправления** (проверяются микротестом до любого длинного прогона):
- VAD с малым `speech_pad_ms`, чтобы стыки попадали в настоящие паузы;
- запас только внутри паузы;
- где стык всё же в речи, запас вместе с текстом соседних слов, которые затем отбрасываются (перекрывающиеся окна);
- для сравнения: без запаса, и запас с текстом без исправления VAD.

Выбранный вариант оформляется поправкой протокола S1b и проходит полную проверку C. Длинный прогон — только после неё.
