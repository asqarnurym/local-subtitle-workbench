# Бэклог: провалы MFA на длинных записях

Составлено 04.11.2026 после завершения прогона S1b.

**Статус: только теоретическая проверка.** Ни одно улучшение из этого документа не
запускалось и не реализовано. MFA и Whisper для него не вызывались. Числа S1b,
замороженные результаты и CLAIM-101…106 не меняются. Формулировки отсюда попадают в
статью и `CLAIM_LEDGER` только после утверждения автором.

Что здесь значит «теоретическая проверка»:
- разбор исходного кода MFA 3.4.3 (`~/.mfa_env`) и его документации;
- расчёт на уже сохранённых результатах S1b;
- сверка с литературой (`docs/LITERATURE_ANNOTATIONS.md`).

Такая проверка показывает, стоит ли пробовать улучшение. Она не доказывает, что оно
работает.

Повторить расчёт (только чтение, ничего не записывает):

```
uv run --no-project --with scipy --with numpy python scripts/mfa_failure_model.py
```

## 1. Что измерено

Запись считается сбоем, если не выровнялся хотя бы один её чанк (протокол S1).

| Длина | Известный текст: чанки | Записи | Текст Whisper: чанки | Записи |
|---|---|---|---|---|
| 1 мин | 0/62 (0 %) | 0/20 | 3/62 (4,8 %) | 2/20 |
| 5 мин | 4/269 (1,5 %) | 3/20 | 10/257 (3,9 %) | 7/20 |
| 10 мин | 7/533 (1,3 %) | 6/20 | 23/501 (4,6 %) | 12/20 |

Без якорения не выровнялись 15, 20 и 20 записей из 20. У CTC сбоев нет ни на одной длине.

## 2. Что показал расчёт

### 2.1. Рост провалов с длиной объясняется числом чанков

Доля провальных чанков от длины почти не зависит. Если считать чанки независимыми, с
долей из L10, то ожидаемое число проваленных записей близко к наблюдаемому:

| Сценарий | 1 мин: ожидание / факт | 5 мин | 10 мин |
|---|---|---|---|
| Известный текст | 0,8 ± 0,9 / 0 | 3,3 ± 1,7 / 3 | 5,9 ± 2,0 / 6 |
| Текст Whisper | 2,7 ± 1,5 / 2 | 9,1 ± 2,2 / 7 | 13,8 ± 2,1 / 12 |

Значит, MFA не становится хуже на длинной записи. Просто в ней больше чанков, а один
провал списывает её целиком. Оговорки: доля взята из L10, поэтому совпадение для L10
отчасти задано расчётом, а короткие записи — префиксы длинных, так что длины не
независимы. Это описание, а не проверка гипотезы.

### 2.2. Правило «вся запись» теряет на порядок больше данных, чем сами провалы

| Длина и сценарий | Слов вне оценки по правилу записи | Слов в провальных чанках |
|---|---|---|
| 5 мин, известный текст | 15,6 % | 1,6 % |
| 5 мин, текст Whisper | 35,0 % | 4,2 % |
| 10 мин, известный текст | 32,7 % | 1,6 % |
| 10 мин, текст Whisper | 63,0 % | 5,3 % |

Границы чанков для этого расчёта взяты из журнала стыков CTC-режимов тех же записей.

### 2.3. При известном тексте провальные чанки — плотная речь, а не плохой текст

Сравнение на L10; медианы, тест Манна — Уитни без поправок, только как описание.

| Показатель | Известный текст: провал / остальные (7 / 526) | Текст Whisper: провал / остальные (23 / 478) |
|---|---|---|
| Ошибка CTC на тех же словах, мс | 40,8 / 42,5 (p = 0,79) | 40,8 / 42,6 (p = 0,52) |
| Доля слов, найденных Whisper | 0,88 / 0,88 (p = 0,55) | 0,84 / 0,87 (p = 0,066) |
| Слов в секунду | 4,54 / 3,82 (p = 0,010) | 3,90 / 3,80 (p = 0,12) |
| Слов в чанке | 117 / 86 (p = 0,033) | 109 / 97 (p = 0,015) |

**Поправка к первоначальной версии.** Сначала причиной считалось несовпадение текста и
звука в чанке. Для записей с якорением это не подтвердилось: CTC выравнивает те же слова
обычным образом, а Whisper находит их не реже. Несовпадение остаётся объяснением только
для режима без якорения, где текст сдвинут намеренно. Для текста Whisper вклад ошибок
распознавания возможен, но не показан.

### 2.4. Провал повторяется, но не всегда

Чанки с теми же границами в L05 и L10 провалились снова в 2 случаях из 3 (известный текст)
и 6 из 7 (текст Whisper). Значит, причина в основном в самом чанке. Исключения (s15,
s27) похожи на случаи у порога. Возможная причина — другая адаптация к диктору при другом
наборе чанков; это не проверено.

## 3. Механизм по исходному коду MFA 3.4.3

- `beam = 10`, `retry_beam = 40`, при неудаче используется второе значение. Оба значения
  действуют в обоих проходах (`alignment/mixins.py`, `kalpy/gmm/align.py`).
- Выравнивание идёт в два прохода: первый без адаптации, затем `calc_fmllr`, затем второй с
  адаптацией к диктору (`alignment/base.py::_align`).
- `NoAlignmentsError` возникает, только если в вызове не выровнялось ничего. Иначе провал
  виден только как отсутствующий TextGrid. Поэтому один и тот же сбой выглядит у нас
  по-разному: ошибка для записи одним чанком и «no TextGrid» для чанка в группе.
- Сообщение самого MFA советует `--beam 100 --retry_beam 400`, а если это не помогло —
  искать проблему в корпусе, словаре или модели через `mfa validate`.
- Документация: beam намеренно низкий, чтобы адаптация обучалась на хороших выравниваниях;
  широкий beam даёт менее оптимальные выравнивания.

**Рабочая гипотеза (вывод, а не измерение).** Это сбой поиска. При отсечении верный путь
может на участке временно отстать от лучшего сверх порога и выпасть. Чем больше слов, тем
больше таких мест, а быстрая редуцированная речь хуже описывается словарём и GMM. Гипотеза
согласуется с §2.3 и §2.4 и с тем, что CTC сбоев не даёт. Прямых логов нет: `--clean` и
удаление временной папки уничтожают их, поэтому причина отдельного сбоя напрямую не
установлена. Подтвердить beam-сбой напрямую удалось только для записей одним чанком
(`NoAlignmentsError`, s34 и s15 в проверке C).

## 5. Открытые вопросы к MF-3

1. **Адаптация.** Если повторить один чанк отдельно, адаптироваться не на чем. Если
   повторить все чанки диктора с широким beam и взять только провальные, адаптация обучится
   и на менее надёжных выравниваниях. Какой вариант лучше, теоретически не решается.
2. **Ложный успех.** Широкий beam может вернуть выравнивание там, где оно плохое. Спасённые
   чанки нельзя считать равными остальным: их точность надо отдельно мерить по ручной
   разметке и публиковать.
3. **BRQE.** Модель обучена только на чанках, которые выровнялись при обычном beam. На
   спасённых чанках её поправки и оценка надёжности не проверены.
4. **Может не помочь.** В отчёте [MFA #677](https://github.com/MontrealCorpusTools/Montreal-Forced-Aligner/issues/677)
   `--beam 100` не исправил сбой.

## 6. Отклонено

- **Поднять beam для всех чанков.** Меняет успешные выравнивания, ломает сравнимость с
  замороженными результатами и, по документации, ухудшает адаптацию.
- **Чинить режим без якорения.** Там текст сдвинут намеренно. Его провалы — результат
  абляции, они показывают необходимость якорения.
- **Лечить beam-настройками неверный текст Whisper.** Сбои `Zero matching tokens` и
  `no speech segments` — не сбои MFA.
- **Заменять числа S1b.** Протокол S1 запрещает перезапуски ради лучших чисел.

## 7. Если автор решит проверять на практике

Порядок для будущего подысследования (условное название S1c):
1. Дождаться окончания цепочки S2 → S3.
2. Записать протокол и критерии до чисел; результаты S1b оставить как есть.
3. Сначала MF-1 и микротест на провальных чанках: 7 при известном тексте и 23 при тексте
   Whisper на L10 (правило микротеста перед долгим прогоном).
4. Сообщать обе оценки: по правилу записи (как в S1b) и по чанкам.

## 8. Как это использовать в статье сейчас

Без новых прогонов и после утверждения автором можно написать в ограничениях:
- провалы растут с длиной из-за числа чанков при почти постоянной доле провальных чанков;
- правило «вся запись» уменьшает выборку, поэтому тесты H1–H4 идут на 7–14 дикторах из 20;
- ошибки в S1b считаются только по выжившим записям.
