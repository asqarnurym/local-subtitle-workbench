# Протокол S1b: длинные записи с исправленной сшивкой чанков

Зафиксирован 03.11.2026 **до** запуска контрольной проверки и прогонов S1b. Это
продолжение S1 (`docs/S1_LONG_RECORDINGS_PROTOCOL.md`): данные, режимы, проверки
H1–H5, правила интерпретации и валидация те же. Отличается только сшивка чанков.
Это **явное отклонение от замороженной версии v1**.

## Почему S1 остановлен

Прогон S1 L01_anchored (20 записей по 60 с, 9 режимов) завершился полностью. Результаты
хранятся в `reports/s1_long_20261103/runs/L01_anchored`, причины сбоев записаны в
`run_record.json`.

Успешных записей: A2 — 0 из 20, B2 — 1 из 20, B1 и A1 — около половины. Обёртка
записала 59 ошибок `MonotonicityError`, все на стыках чанков.

Причина:
- Каждый чанк получает аудио с запасом 0,5 с, а текст только свой.
- В запасе звучит речь соседнего чанка, которой нет в тексте.
- Выравниватель обязан разместить все слова текста, поэтому растягивает крайнее слово на эту речь.
- После этого два чанка претендуют на один и тот же звук.
- Замороженная сшивка (`reconcile_chunk_alignments`) в этом случае не разрешает конфликт, а объявляет сбоем всю запись.

В основном бенчмарке клипы короче 30 с, поэтому сшивка там не применялась. На L05 и
L10 стыков в 5–10 раз больше, и проверки H1–H5 стали бы нетестируемыми. По
решению автора прогон остановлен до L01_noanchor; пустая папка этого прогона удалена.

## Исправление (`scripts/seam_safe.py`)

1. Каждое слово обрезается до основной части своего чанка, `[start, end]`, то есть
   без запаса. Чанкер отнёс слово именно к этому участку. Если слово целиком лежит в
   запасе, оно остаётся длиной 1 мс на краю основной части. Фонемы слова линейно
   переносятся в новый интервал.
2. Результат сшивается замороженной функцией.
3. Если она всё равно отказывает или теряет слово, применяется монотонный проход:
   - начала слов строго возрастают (шаг не меньше 1 мс);
   - длительности положительные;
   - перекрытия убираются.

   Результат всегда валиден, и все выровненные слова сохраняются.
4. У записи из одного чанка обрезки нет. Её результат **совпадает** с замороженной
   сшивкой, поэтому основной бенчмарк этим исправлением не затрагивается (это проверено тестом).

Пакет `subtitle_workbench` не меняется. Обёртка подставляет новую сшивку во время
прогона (`seam_safe_reconciliation`).

Для каждой записи журнал фиксирует:
- число чанков и время стыков;
- отказала бы замороженная сшивка или нет;
- сколько слов обрезано и максимальный сдвиг;
- применялся ли монотонный проход.

Журнал пишется в `run_record.json` (`seam_reconciliation_log`).

Других изменений нет. Сбои MFA («no TextGrid» для чанка) остаются сбоями записи.

## Проверка A: модульные тесты (`tests/test_seam_safe.py`)

- один чанк даёт результат, идентичный замороженному;
- случай s02 («everything» раньше «with»), на котором замороженная сшивка падает,
  даёт валидную шкалу времени, и слово остаётся в своём чанке;
- слово целиком в запасе сохраняется;
- 300 случайных «мусорных» входов дают валидную полную шкалу без потери слов;
- подмена сшивки корректно снимается после блока.

## Проверка C: стоимость стыка на реальных данных (`scripts/s1b_seam_check.py`)

Берутся 20 записей L01 из сборки S1. Каждая выравнивается дважды:
- **одним чанком**;
- **чанками по умолчанию** (≤ 30 с) с исправленной сшивкой.

Аудио, Whisper, якорение и текст одинаковые. Режимы A2 и B2 (MFA). Ошибки сравниваются
на одних и тех же словах:
- **около стыка** — эталонное начало слова в пределах 1 с от стыка;
- **вдали от стыка**.

**Критерий прохождения (до чисел):** средняя по всем границам слов около стыков ошибка
при нарезке превышает ошибку одним чанком не более чем на **10 мс**, отдельно для A2 и
для B2. Число случаев, где замороженная сшивка отказала бы, и сбои MFA сообщаются.

Если проверка C не пройдена, длинный прогон не запускается, а результат сообщается
автору.

*Поправка 03.11.2026, до получения каких-либо метрик проверки C.* Первый запуск
проверки C (05:16–06:10) остановился до записи результатов. В варианте «одним чанком»
MFA не нашёл выравнивания 60-секундной записи диктора s34 (`NoAlignmentsError` при
beam 10 / retry beam 40, во всех трёх попытках). Так как в вызове MFA одна запись,
эта ошибка обрывала весь процесс.

Это детерминированный отказ выравнивания, а не сбой инфраструктуры, поэтому теперь
он, как и ошибка сшивки, считается сбоем этой записи (`IsolatingAligner`, по одному
вызову на запись). Запись исключается из парного сравнения и сообщается. Нативные
падения MFA по-прежнему останавливают процесс (правило 4 протокола S1). Та же
обработка действует в прогонах S1b. Критерий прохождения не меняется.

*Вторая поправка 03.11.2026, тоже до получения метрик.* Второй запуск (06:16–08:14)
выровнял все четыре варианта, но упал при записи `seam_check.json`: если запись
не выровнялась только в одном варианте, в отчёт попадал список слов другого варианта,
который не сериализуется в JSON. Метрики не были выведены. Теперь для такого диктора
в отчёт пишется только текст сбоя (тест `tests/test_s1b_seam_check.py`). Расчёт метрик
и критерий не меняются; проверка C запускается заново.

## Прогоны S1b

Если проверки A и C пройдены, запускается:

```
python scripts/s1_long_recordings.py build --output-dir reports/s1b_long_20261103
python scripts/s1_long_recordings.py run   --output-dir reports/s1b_long_20261103 --reconciler seam_safe
```

Сборка детерминирована. Хэши её файлов должны совпасть со сборкой S1, и это сверяется.

Затем выполняются `analyze` и `verify` по протоколу S1. Все прогоны в каталоге обязаны
использовать одну сшивку, иначе обёртка отказывает.

Результаты S1 (L01_anchored с замороженной сшивкой) не удаляются. Они сообщаются как
поведение версии v1 на длинных записях.

## Поправка 3 (03.11.2026, до полной проверки C с новым методом): склейка `stitch`

Автор дал команду продолжать. Метод — `scripts/seam_stitch.py`, тесты —
`tests/test_seam_stitch.py`. Пакет не меняется: всё подставляется обёрткой
`stitched_pipeline()`.

1. **VAD.** Silero-VAD с `speech_pad_ms = 30` вместо 400 по умолчанию.
2. **Перекрытие.** Каждый кусок получает слова соседних кусков с обеих сторон, пока они
   не покроют не меньше 3 с. Граница аудио ставится посередине промежутка до следующего
   слова.
3. **Склейка.**
   - На каждом стыке ищется точка согласия: слово с тем же текстом и границами в пределах
     20 мс в обеих дорожках, ближайшее к стыку, но не крайнее в дорожке.
   - Дорожка A берётся до этого слова включительно, дорожка B — после него. Затем
     выполняется монотонный проход.
   - Если точки нет, разрез идёт по времени стыка. Это записывается в журнал и сообщается.
4. **Запись из одного куска** сшивается замороженной функцией, как прежде.

Критерий проверки C не меняется: превышение около стыков ≤ 10 мс отдельно для A2 и B2,
на тех же 20 записях L01 и с тем же расчётом.

**Порядок запуска:**
1. Пробный прогон на двух записях — s07 (детерминированный сбой) и s20 (провальные
   стыки) — в неверсионируемый каталог. Он проверяет весь путь, включая запись отчёта.
   Его числа в выводы не входят.
2. Полная проверка:
   ```
   python scripts/s1b_seam_check.py --output-dir reports/s1b_seam_check_stitch_20261103 --reconciler stitch --workers 4
   ```

`--workers 4` выравнивает четыре набора (A/B × чанки/один кусок) в параллельных процессах.
У каждого процесса своя копия каталога MFA (`MFA_ROOT_DIR`) с теми же моделями и
настройками. Вызовы MFA те же: один на запись, `num_jobs = 1`.

Если проверка пройдена, длинный прогон S1b идёт с `--reconciler stitch`. Его объём автор
утверждает отдельно. Если не пройдена, длинный прогон не запускается, а результат
сообщается автору.
