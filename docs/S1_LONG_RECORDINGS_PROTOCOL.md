# Протокол S1: длинные записи (дрейф и якорение)

Зафиксирован 03.11.2026 **до** запуска моделей на этих данных (план §4, этап E2).
Код: `scripts/s1_long_recordings.py`; ядро пайплайна и `speech_benchmark.py` не меняются.

## Вопросы

1. **Дрейф.** Растёт ли ошибка границ к концу длинной записи?
2. **Длина.** Хуже ли выравниваются одни и те же слова, если они находятся в длинной
   записи, а не в короткой?
3. **Якорение.** Насколько привязка известного текста к словам Whisper помогает в
   сценарии A по сравнению с равномерным распределением текста по длительности
   записи?

## Данные

- 20 **тестовых** дикторов Buckeye (`reports/buckeye_split_20260401.json`). Обучающие
  дикторы BRQE не используются.
- Для каждого диктора клипы `data/corpora/buckeye/<диктор>*` берутся в порядке
  идентификаторов, то есть по порядку дорожек и внутри дорожки. Клипы с пустым
  аудио пропускаются, их список записывается.
- Подряд идущие клипы склеиваются без вставленных пауз. Запись длины L — это
  кратчайший начальный отрезок последовательности с суммарной длительностью ≥ L.
  Длины: **L01 = 60 с, L05 = 300 с, L10 = 600 с**. Короткие записи являются
  префиксами длинных: первые слова L10 совпадают со словами L01 и L05, вместе с
  эталонными временами.
- Эталонная разметка — это разметка клипов, сдвинутая на смещение клипа в склейке.
  Склейка — производные данные: стыки клипов не являются естественной речью.

## Прогоны (каждая длина — отдельный прогон)

| Вариант | Режимы | ASR |
|---|---|---|
| `anchored` | все 9 режимов основного бенчмарка (B0, B1, B2, A1, A2, `*_const`, `*_brqe`) | Whisper large-v3, CUDA |
| `noanchor` | A2, A2_const, A2_brqe | нет: пустая гипотеза, весь текст распределяется пропорционально длине слов |

Во всех прогонах одинаковы: `run_benchmark` основного бенчмарка, BRQE из
`models/brqe`, seed 42, 2 000 bootstrap-повторов, MFA с `num_jobs=1` и до 3 попыток,
VAD и нарезка на чанки по умолчанию (≤ 30 с, паддинг 0,5 с). Сбой фиксируется
по записи и не исключается. Если в замороженном пайплайне не выровнялся хотя бы один
чанк, сбоем считается вся запись.

*Четвёртая поправка 03.11.2026, до получения каких-либо метрик.* Первый прогон
(L01, режим B1) прервался целиком. Замороженный `align_requests` не превращает
ошибку согласования чанков одной записи (`MonotonicityError`: слова из соседних
чанков CTC пересеклись по времени) в сбой этой записи, а прерывает весь пакет. На
клипах это не проявлялось, так как там один чанк. Теперь обёртка
(`IsolatingAligner`) вызывает замороженный выравниватель отдельно для каждой
записи. `ChunkingError` записывается как сбой этой записи (список в
`run_record.json`), остальные ошибки по-прежнему останавливают прогон. В каждом
прогоне одна запись на диктора, MFA и раньше запускался один раз на диктора,
поэтому вычисления не меняются. Пустая папка прерванного прогона удалена.

## Анализ

Для каждой пары «эталонное слово — предсказанное слово» используется сопоставление
из основной метрики (`_align_token_sequences`). Ошибка — модуль ошибки начала и конца,
в мс. Позиция слова — эталонное время его начала в записи.

**Основные проверки** (точный двусторонний знаково-ранговый тест Уилкоксона,
единица наблюдения — диктор, поправка Холма по пяти проверкам):

| ID | Сравнение | Величина на диктора |
|---|---|---|
| H1 | Дрейф A2 | MAE слов на минутах [8, 10) минус MAE на [0, 2) в L10 |
| H2 | Дрейф B2 | то же для B2 |
| H3 | Длина, A2 | MAE слов из L01 при выравнивании внутри L10 минус MAE тех же слов в L01 |
| H4 | Длина, B2 | то же для B2 |
| H5 | Якорение | MAE слов A2 `noanchor` минус A2 `anchored`, обе в L10 |

Диктор без результата в одном из условий исключается из соответствующей проверки,
число исключённых сообщается. Если пар меньше 6, проверка «не тестируема»: при
n ≤ 5 минимальное точное p ≥ 0,0625.

**Описательно** (без проверки гипотез):
- для каждой длины и режима: MAE, Acc@20ms, покрытие, сбои, CI по дикторам;
- в L10 по минутам 0–10: MAE A2, B2 и их BRQE-вариантов (рисунок);
- выигрыш BRQE над базовым MFA по длинам, ROC-AUC головы надёжности;
- сбои и покрытие в `noanchor` против `anchored` (доля якорей бенчмарком не сохраняется и не сообщается);
- время работы и RTF только для прозрачности.

## Правила интерпретации (до чисел)

1. Замороженные результаты, веса и CLAIM-101…106 не меняются. Числа S1 становятся
   новыми утверждениями только после утверждения формулировок автором.
2. Отсутствие дрейфа не утверждается по незначимому тесту: сообщаются величина
   эффекта и CI.
3. Сбои публикуются вместе с MAE. MAE считается только по успешным записям, поэтому
   его нельзя читать в отрыве от доли сбоев.
4. Если процесс падает из-за инфраструктуры (нативный сбой MFA или CTC, нехватка
   памяти), тот же прогон перезапускается с тем же кодом, и перезапуск записывается.
   Перезапуски ради лучших чисел запрещены.
5. Результаты на склейках не переносятся напрямую на естественные лекции; это
   ограничение указывается.

## Валидация

1. **Сборка:** для каждой записи аудио побайтово равно склейке клипов. Разметка после
   чтения штатным парсером совпадает со сдвинутой разметкой клипов с точностью
   0,201 мс; максимальное отклонение каждой записи пишется в `build.json`. Проверяется,
   что короткие записи являются префиксами длинных (с тем же допуском). Текст слов и
   фонем во всех проверках должен совпадать точно.

   *Поправка 03.11.2026, до запуска моделей.* Сначала был задан допуск 1 мкс.
   Первая сборка остановилась на этой проверке: штатный парсер `parse_textgrid`
   округляет времена до 0,1 мс, а смещения клипов кратны 1/16 000 с. Эталон
   склейки и эталон клипа округляются по одному разу, поэтому они расходятся не
   больше чем на 0,1 мс; допуск исправлен на это значение. Это та же точность,
   что у эталонов клипов основного бенчмарка. Частично записанные файлы упавшей
   сборки удалены.

   *Вторая поправка 03.11.2026, до запуска моделей.* Повторная сборка остановилась
   на точной проверке префикса у `s03`. Если следующий клип начинается сразу после
   конца предыдущего слова, парсер при перекрытии в 0,1 мс обрезает конец этого
   слова (`s03`, слово 989: 301,4673 → 301,4672 с в L10). Это затрагивает только
   последнее слово короткой записи. Префикс теперь проверяется с допуском 0,101 мс,
   а совпадение текста и фонем по-прежнему требуется точное.

   *Третья поправка 03.11.2026, до запуска моделей.* У `s09` в L05 сборка
   остановилась на отклонении 0,11 мс (слово «kinda», конец 151,1227 против
   151,1228 с). Здесь два округления наложились на обрезку перекрытия. Чтобы не
   подбирать допуск под каждый новый случай, он задан как сумма этих эффектов
   парсера: 2 × 0,05 мс на округление плюс 0,1 мс на обрезку, итого 0,201 мс.
   Ошибка сдвига или порядка слов дала бы отклонения от десятков миллисекунд,
   такие ошибки проверка по-прежнему ловит. После каждой поправки неполные файлы
   сборки удалялись.
2. **Анализ:** MAE каждой записи, пересчитанный из предсказаний, совпадает со
   строкой бенчмарка (`benchmark_utterances.json`, округление до 0,001 мс).
3. **Отдельная проверка** (`--verify`, отдельный процесс): повторный расчёт анализа
   и сравнение с записанным; хэши входов, сборки и кода; точные p-значения
   сверяются с полным перебором 2ⁿ знаков.
4. **Происхождение (R4):** состояние Git до и после (только чистое дерево), хэши
   скриптов, `uv.lock`, весов BRQE, исходных клипов и производных файлов. Уже
   завершённые прогоны не перезаписываются.
